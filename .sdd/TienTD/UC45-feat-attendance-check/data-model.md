## Schema Review

### Table: `attendances`

**Owner**: Member 3 - TienTD  
**Purpose**: Điểm danh sự kiện  
**Soft Delete**: No (immutable participation data)

#### Columns

| Column | Type | Constraints | UC45 Usage |
|--------|------|-------------|------------|
| `id` | INT | PRIMARY KEY, AUTO_INCREMENT | ✅ Generated by database |
| `application_id` | INT | UNIQUE, FOREIGN KEY → applications.id | ✅ **INPUT**: Từ request (single/bulk) |
| `status` | ENUM('PRESENT', 'ABSENT') | NOT NULL | ✅ **FIXED**: Always 'PRESENT' cho check-in |
| `volunteer_hours` | DECIMAL(5,2) | NULL | ❌ **NULL**: UC45 không set, update sau |
| `checked_in_by` | INT | FOREIGN KEY → users.id | ✅ **FROM JWT**: Staff ID từ auth token |
| `checked_in_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | ✅ **AUTO**: Database timestamp |
| `notes` | TEXT | NULL | ✅ **OPTIONAL**: Từ request body |

#### Indexes

Existing indexes (from DATABASE.md):
- **PRIMARY KEY** (`id`): Unique identifier
- **UNIQUE** (`application_id`): Enforce one check-in per application
- **INDEX** (`checked_in_by`): Fast lookup by Staff
- **INDEX** (`checked_in_at`): Time-based queries

**Performance Impact**:
- UNIQUE constraint trên `application_id` → Duplicate check-in attempts throw error immediately (database-level)
- Index trên `checked_in_by` → Fast audit queries ("Who checked in this volunteer?")
- Index trên `checked_in_at` → Fast time-range queries (UC46: View attendance history)

## Business Rules & Constraints

### Constraint 1: One Check-in Per Application

**Database Level**:
```sql
UNIQUE INDEX `attendances_application_id_unique` ON `attendances` (`application_id`)
```

**Behavior**:
- ✅ First check-in: INSERT succeeds
- ❌ Duplicate check-in: INSERT fails với `ER_DUP_ENTRY` error (MySQL code 1062)
- ✅ Service layer catches error → HTTP 409 Conflict

**Example**:
```javascript
// First call: Success
POST /api/v1/attendances/123/check-in
→ 201 Created

// Second call: Conflict
POST /api/v1/attendances/123/check-in
→ 409 Conflict: "Volunteer already checked in"
```

---

### Constraint 2: Only Approved Applications

**Validation Logic**:
```javascript
// AttendanceService.checkIn()
const application = await applicationRepository.getById(applicationId);

if (application.status !== 'APPROVED') {
  throw new BadRequestError(
    `Cannot check-in application with status: ${application.status}. Only APPROVED applications can be checked in.`
  );
}
```

**State Dependency**:
```
applications.status = 'APPROVED' 
  ↓ (prerequisite)
attendances record creation
```

UC24 (Approve Application) MUST run trước UC45 (Attendance Check).

---

### Constraint 3: Event Status Validation

**Validation Logic**:
```javascript
// AttendanceService.checkIn()
const event = await eventRepository.getById(application.event_id);

if (event.status === 'COMPLETED' || event.status === 'CANCELLED') {
  throw new BadRequestError(
    `Cannot check-in for event with status: ${event.status}. Event must be PUBLISHED or IN_PROGRESS.`
  );
}
```

**Valid Event States for Check-in**:
- ✅ `PUBLISHED`: Pre-event check-in (early arrivals)
- ✅ `IN_PROGRESS`: During event check-in (primary use case)
- ❌ `DRAFT`: Event not ready
- ❌ `COMPLETED`: Event ended
- ❌ `CANCELLED`: Event cancelled

---

### Constraint 4: Organization Authorization

**Authorization Logic**:
```javascript
// AttendanceService.checkIn()
await authorizationService.checkStaffOrganizationAccess(staffId, event.id);
```

**Rule**:
- Staff MUST belong to same organization as event
- Reuses existing `authorization.service.js` (from UC24-UC25)

**Example**:
```
Staff A (organization_id: 1) attempts to check-in for Event X (organization_id: 2)
→ 403 Forbidden: "Staff can only check-in for events of their organization"
```

---

### Constraint 5: Immutability

**Rule**: Sau khi attendance record được tạo, KHÔNG được UPDATE `status` hoặc `checked_in_at`.

**Rationale**:
- Audit trail integrity
- Attendance data dùng cho certificate generation (UC53)
- Prevent tampering với participation history

**Only Allowed Update**:
- `volunteer_hours`: NULL → actual hours (future UC or manual update)
- `notes`: Update/append notes (low priority)

**Example**:
```sql
-- ❌ NOT ALLOWED
UPDATE attendances SET checked_in_at = '2026-06-29 10:00:00' WHERE id = 123;

-- ✅ ALLOWED (future UC)
UPDATE attendances SET volunteer_hours = 4.5 WHERE id = 123 AND volunteer_hours IS NULL;
```

## UC45-Specific Data Operations

### Operation 1: Single Check-in

**SQL Execution**:
```sql
-- Step 1: Validate application
SELECT id, event_id, status, user_id 
FROM applications 
WHERE id = ? 
  AND status = 'APPROVED';

-- Step 2: Get event details
SELECT id, organization_id, status 
FROM events 
WHERE id = ?;

-- Step 3: Authorization check (via UserRepository + OrganizationRepository)
-- (Multiple queries, handled by authorization.service.js)

-- Step 4: Insert attendance record
INSERT INTO attendances (
  application_id, 
  status, 
  volunteer_hours, 
  checked_in_by, 
  checked_in_at, 
  notes
) VALUES (
  ?,            -- application_id from request
  'PRESENT',    -- Fixed value
  NULL,         -- Not set by UC45
  ?,            -- Staff ID from JWT
  NOW(),        -- Current timestamp
  ?             -- Optional notes from request
);
```

**Prisma Equivalent**:
```javascript

    status: 'PRESENT',
    volunteer_hours: null,

    checked_in_at: new Date(),

  }

```

### Operation 2: Bulk Check-in

**Pseudo-code**:
```javascript
async bulkCheckIn(applicationIds, staffId, data) {
  const results = [];
  
  for (const appId of applicationIds) {
    try {
      // Validate + Insert individually (no transaction wrap)
      const attendance = await this.checkIn(appId, staffId, data);
      results.push({
        application_id: appId,
        status: 'success',
        attendance_id: attendance.id
      });
    } catch (error) {
      results.push({
        application_id: appId,
        status: 'error',
        error: error.message
      });
    }
  }
  
  return {
    total: applicationIds.length,
    succeeded: results.filter(r => r.status === 'success').length,
    failed: results.filter(r => r.status === 'error').length,
    results
  };
}
```

**Performance**:
- 50 INSERTs × 50ms = ~2.5s (sequential)
- Có thể optimize với Prisma `createMany()` nếu cần (batch insert)

### Operation 3: Get Attendance Checklist

**Purpose**: Frontend fetch danh sách volunteers để hiển thị UI với search + checkbox.

**SQL Query**:
```sql
SELECT 
  app.id AS application_id,
  u.id AS volunteer_id,
  u.full_name AS volunteer_name,
  u.avatar_url AS volunteer_avatar,
  att.id AS attendance_id,
  CASE 
    WHEN att.id IS NOT NULL THEN TRUE 
    ELSE FALSE 
  END AS is_checked_in,
  att.checked_in_at
FROM applications app
INNER JOIN users u ON app.user_id = u.id
LEFT JOIN attendances att ON app.id = att.application_id
WHERE app.event_id = ?
  AND app.status = 'APPROVED'
ORDER BY 
  is_checked_in ASC,  -- Unchecked volunteers first
  u.full_name ASC;
```

**Prisma Equivalent**:
```javascript
// AttendanceRepository.getChecklistByEventId()
const checklist = await prisma.applications.findMany({
  where: {
    event_id: eventId,
    status: 'APPROVED'
  },
  include: {
    user: {
      select: {
        id: true,
        full_name: true,
        avatar_url: true
      }
    },
    attendance: {
      select: {
        id: true,
        checked_in_at: true
      }
    }
  },
  orderBy: [
    { attendance: { id: 'asc' } }, // NULL first (unchecked)
    { user: { full_name: 'asc' } }
  ]
});

// Transform to UI-friendly format
return checklist.map(app => ({
  application_id: app.id,
  volunteer_id: app.user.id,
  volunteer_name: app.user.full_name,
  volunteer_avatar: app.user.avatar_url,
  is_checked_in: !!app.attendance,
  attendance_id: app.attendance?.id || null,
  checked_in_at: app.attendance?.checked_in_at || null
}));
```

## Relationships & Foreign Keys

### attendances → applications (Many-to-One)

```sql
FOREIGN KEY (application_id) REFERENCES applications(id) ON DELETE RESTRICT
```

**Behavior**:
- ✅ Attendance record tham chiếu đến application
- ❌ KHÔNG thể delete application nếu có attendance record (ON DELETE RESTRICT)
- ✅ Cascade soft delete: application.status = 'CANCELLED' không ảnh hưởng attendance (immutable audit data)

### attendances → users (Many-to-One via checked_in_by)

```sql
FOREIGN KEY (checked_in_by) REFERENCES users(id) ON DELETE RESTRICT
```

**Behavior**:
- ✅ Attendance record lưu lại Staff ID đã thực hiện check-in
- ❌ KHÔNG thể delete Staff user nếu đã check-in volunteers (ON DELETE RESTRICT)
- ✅ Soft delete Staff: users.is_active = false không ảnh hưởng attendance history

## Analytics Queries

### Query 1: Attendance Rate by Event

```sql
SELECT 
  e.id AS event_id,
  e.title AS event_title,
  COUNT(DISTINCT app.id) AS total_approved,
  COUNT(DISTINCT att.id) AS total_checked_in,
  ROUND(COUNT(DISTINCT att.id) * 100.0 / COUNT(DISTINCT app.id), 2) AS attendance_rate_percent
FROM events e
LEFT JOIN applications app ON e.id = app.event_id AND app.status = 'APPROVED'
LEFT JOIN attendances att ON app.id = att.application_id
WHERE e.id = ?
GROUP BY e.id, e.title;
```

**Example Output**:
```
event_id | event_title          | total_approved | total_checked_in | attendance_rate_percent
---------|----------------------|----------------|------------------|------------------------
101      | Beach Cleanup 2026   | 50             | 48               | 96.00
```

---

### Query 2: Staff Check-in Performance

```sql
SELECT 
  u.id AS staff_id,
  u.full_name AS staff_name,
  COUNT(att.id) AS total_check_ins,
  DATE(att.checked_in_at) AS check_in_date
FROM attendances att
INNER JOIN users u ON att.checked_in_by = u.id
WHERE DATE(att.checked_in_at) = CURDATE()
GROUP BY u.id, u.full_name, DATE(att.checked_in_at)
ORDER BY total_check_ins DESC;
```

**Use Case**: Monitor Staff workload tại check-in counter.

---

### Query 3: Late Check-ins Detection

```sql
SELECT 
  app.id AS application_id,
  u.full_name AS volunteer_name,
  e.start_date AS event_start,
  att.checked_in_at,
  TIMESTAMPDIFF(MINUTE, e.start_date, att.checked_in_at) AS minutes_late
FROM attendances att
INNER JOIN applications app ON att.application_id = app.id
INNER JOIN events e ON app.event_id = e.id
INNER JOIN users u ON app.user_id = u.id
WHERE att.checked_in_at > e.start_date
  AND TIMESTAMPDIFF(MINUTE, e.start_date, att.checked_in_at) > 15
ORDER BY minutes_late DESC;
```

**Use Case**: Identify volunteers who arrived late (>15 minutes after event start).
